K-cluster and DBscan were tested in tandem with RANSAC for filtering important keypoints. K-clusters has an unclear tuning process, with certain cluster counts doing better than others, but not in an increasing fashion but a random alternating pattern. In general, DBscan seems to be more efficient since kclusters demands a higher count around 12 at least and with ease selects matches that are more accurate (at worst 2 squares off with most 1 or less) while k-clusters typically is 4-5 squares off. This is likely thanks to the epsilon parameter which allows DBscan to eliminate clusters with points too far from one another, while kclusters compacts points together based on how many clusters are expected to be taken from the total. Therefore, with kclusters it's less straight forward and computationally expensive (b/c more clusters are required) to compact the points together and filter out squares with inaccurately spread out matches). For now, DBscan will be moved forward.

 Found out a major cause of solve inaccuracy/sensitivty to movement was b/c update step in the motion estimation function involved multiplying perturbation into current pose and returning that instead of delta directly. So update step was T_n = exp(pert)*T_o*T_o instead of T_n=exp(pert)*T_o. The return of the function was being treated as a pertubation, not an updated state, which means it intrinsically induced additional/nonexistent motion, exascerbating any numerical instability present and creating a runaway effect. Testing didn't pick this up b/c only one perturbation was solved for, not multiple, and the identity matrix was treated as the starting pose, so doubling up on it wouldn't have an effect (I*I=I!). Lesson is: for a function that involves system updates, test it over multiple updates!!!

Discovered other bug occurred by passing previous color frame to be transformed into current grey frame, which hurt stability since update was lagging behind on keypoints but not depth. Fixed by ensuring current color frame was transformed into current grey frame so update is properly synchronized with current state values instead of being split between past and present.

A quick aside: kalman filter was found to be not quite appropriate for current pipeline because it requires both a prediction from a model, which is possessed, but also an independent measurement to reference and assert the integrity of the model's predictions. In this pipeline, there is no direct measurement that can be received to assert to current pose outside of the sensor information already utilized in the prediction model. If there was a separate IMU sensor or some GNSS or other ground truth info to reference a prediction against, weighting for how much to trust the current prediction of the motion model or not could be established, but in this case there is not. Also, b/c keypoints constantly change in count and id, a kalamn filter cannot be applied to smoothen points received between frames either. Having a direct reference for a predicted output would make this all possible, like an output variable of steam pressure in a chemical plant whee a prediction model stabilizes the measured pressure against noise, but that is not the case here. Definitely something that may be attempted in a dual vision-imu pipeline in the future!!

Another bug found. When the 3D point set is formed from the newest keypoints, points with depths that are too low and can hurt solver accuracy are filtered out. Unfortunately, solver was not receiving point set with invalid depths filtered out (called pts_curr_valid) but was just getting the raw new keypoints, which both could have invalid depths but were not properly corresponding 1 to 1 with 3d point set.

Improved motion model by changing how 3d projection works - real sense provides subpixel-accurate feature coordinates, but depth was previously sampled using integer pixel indexing (nearest neighbor) with 
    u_i = np.clip(u.astype(int), 0, depth.shape[1]-1)
    v_i = np.clip(v.astype(int), 0, depth.shape[0]-1) so subpixels would snap to depth of nearest pixel instead of interpolating it from adjacent pixels.

This caused discontinuous depth values as features moved across pixel boundaries, leading to jagged 3D point estimates, exascerbating previous depth issues encountered. Replaced nearest-neighbor depth lookup with bilinear interpolation at subpixel feature coordinates.
So now, depth values now vary smoothly with feature motion and 3D point reconstruction is more consistent. Therefore, it is likely residuals and optimization behave more stably.
